# 记忆系统优化（Mem）

提示词：`开始 Mem-DayN`

目标：在现有 PostgreSQL 会话历史上，把「最近 N 轮截断」升级为**可隔离、可预算、可追问**的记忆系统。  
第一版只做短时会话记忆 + 摘要 + 情景快照；**不做**自动长期事实抽取，**不重做** Alarm 步骤 Checkpoint（Harness H5 已有）。

> 更完整的平台级方案见 [记忆系统完善计划.md](./记忆系统完善计划.md)。本文是**可跟做的第一版**。  
> **前置：** Harness H5（Run/Event/Checkpoint）与 H6（Policy/脱敏）已落地；Mem 在其之上做「会话记忆」，勿另起平行 Run 台账。

---

## 0. 你要先建立的概念

```text
短时记忆 Short-term     = 当前会话最近对话原文（给模型看「聊过什么」）
摘要记忆 Summary        = 更早轮次的结构化压缩（省 Token，不丢关键事实）
情景记忆 Episodic       = 某次任务结论（告警实体、证据、页码）——支持跨轮追问
工作记忆 / 执行状态     = 当前 Run 中间态（tool_fail_counts、pipeline step）
长时记忆 Long-term      = 跨会话稳定事实（偏好等）——第二版再做
语义缓存 Cache          = 性能优化，不是用户记忆，必须按用户隔离
```

**不要把「当前任务中间状态」塞进短时对话消息表。**  
对话消息只存用户说了什么、助手回了什么。

**两类「状态」不要混用（Harness 之后尤其重要）：**

| 类型 | 表 / 机制 | 生命周期 | 本专题是否做 |
|------|-----------|----------|--------------|
| 会话情景（追问） | `chat_sessions.last_alarm_episode` 等 | 跨轮、跟 `session_id` | **做（Day8）** |
| Run 步骤恢复 | `harness_checkpoints` | 同一次 `run_id` 内 resume | **已有，本专题不改 schema** |
| Chat 图内工作态 | LangGraph 进程内 | 单次请求结束即丢 | 第一版不接持久 Checkpointer |

第一版落地映射：

| 概念 | 落地点 |
|------|--------|
| 短时 | `chat_messages` + Token Budget 装配 |
| 摘要 | `session_summaries`（可先 JSONB 一列） |
| 情景 | session 上 `last_alarm_episode`（或独立小表）；**不是** `harness_checkpoints` |
| 工作记忆 | Chat：仍进程内；Alarm 步骤：已有 harness checkpoint，本专题不重做 |
| Run 追溯 | **复用** `harness_runs` / `harness_run_events`；消息挂 `run_id` |
| 长时 | 第二版 `memory_facts` |
| 缓存 | `SemanticCache` 增加 `user_id`/`session` scope |
| 脱敏 | 写入会话/Trace 前对齐 H6 `DataPolicy`（禁止把密钥写进 metadata） |

## 1. 建设原则

- PostgreSQL 是会话与情景的真相源；向量库不存聊天真相。
- 所有读写必须能落到 `user_id`（开发期可用 Header 注入）。
- 取消共享 `default` 会话。
- Prompt 按 **Token 预算**装配，不以轮数为主。
- 短时记忆 ≠ 任务中间状态 ≠ Harness Checkpoint。
- **不新建**与 `harness_runs` 平行的 `agent_runs` 台账；Day5 只挂 `run_id`。
- 改造入口：HTTP Adapter + `session_service` + `services/chat`（ChatExecutor 仍调 `run_astream`，改 chat 层即可惠及 Harness）。
- **不要**在 `AgentRuntime` 里塞记忆装配逻辑。
- 第一版不自动把模型推断写成永久事实。
- API 形状尽量兼容：可继续传 `session_id`，服务端把它当 `session_key`。

## 3. 目标数据（第一版最小集）

### 3.1 `chat_sessions`（在现有表上演进）

| 字段 | 说明 |
|------|------|
| `session_id` | 对外会话键（可继续当 PK，或日后拆成内部 UUID + session_key） |
| `user_id` | **必填**，隔离键 |
| `status` | active / ended / deleted（可先字符串） |
| `created_at` / `updated_at` / `ended_at` | 生命周期 |

> Day1～2 为降低迁移成本：**先保留 `session_id` 作 PK**，加上 `user_id` 与唯一约束 `(user_id, session_id)` 语义（若 session_id 全局唯一，则查询一律 `WHERE session_id=? AND user_id=?`）。

### 3.2 `chat_messages`

现有 `role` / `content` / `created_at` 保留，Day5 增加：

| 字段 | 说明 |
|------|------|
| `intent` | 路由意图 |
| `engine` | chat_react / rag / alarm / crew |
| `run_id` | 关联一次执行 |
| `metadata` | JSONB，可选放 sources 摘要 |

工具明细优先放已有 `harness_run_events` 或消息 `metadata`（**不要**新建 `agent_runs`）。

### 3.3 `session_summaries`（Day6）

| 字段 | 说明 |
|------|------|
| `session_id` | 所属会话 |
| `summary` | JSON：topic / known_facts / decisions / unresolved |
| `through_message_id` | 已覆盖到的最后消息 |
| `updated_at` | |

### 3.4 Alarm 情景（Day8）— 会话级，非 Checkpoint

可先存在 `chat_sessions` 的 JSON 列 `last_alarm_episode`，或独立小表。至少包含：

- `config_id`、monitor url、级别  
- 证据摘要、当前页码、playbook 提示  
- 可选：最近一次相关 `run_id`（指向 `harness_runs`）  
- `updated_at`

**明确不做：** 把聊天历史或追问结果写进 `harness_checkpoints`；不改 H5 的 name/幂等约定。

## 4. 上下文装配顺序（Day4 起统一）

```text
System Prompt
+ 会话摘要（若有）
+ 最近原始消息（Token 预算内）
+ 当前问题
(+ Day8：若走 Alarm 追问，附加 last_alarm_episode)
<= context_token_budget
```

统一入口建议：`app/services/context_builder.py`  
`build_context(user_id, session_id, query, agent_type, budget) -> StructuredContext`

挂载点：`services/chat.py`（及 RAG/Crew 同类入口）。Router / Chat / RAG / Crew 逐步改用它。  
**不要**改 `AgentRuntime` 来装配记忆；Harness Adapter 继续传 `session_id` / `db` 即可。

写入消息与 metadata 前应对齐 H6 `DataPolicy` 脱敏规则。

## 5. 身份约定（Day1）

当前只有 API Key，没有登录用户。第一版约定：

```http
X-User-Id: demo-user-a
```

- 未开启严格模式时：缺省可回退 `anonymous`（仅本地），但**禁止**再写入共享 `default` 会话。  
- `ChatRequest.session_id`：改为可选；为空则服务端 `uuid4` 新建并在响应 `meta.session_id` 返回。  
- 所有 session 读写：`user_id + session_id` 同时匹配。

## 6. 实现步骤（按日拆解，你来写）

### Mem-Day1 — 身份与取消 default

**目标：** 没有「全站共用一个 default 会话」；请求能识别用户。

1. `schemas.ChatRequest`：`session_id` 改为 `Optional[str] = None`（去掉默认 `"default"`）。  
2. `ChatResponse.meta` 或顶层增加回传 `session_id`（新建时必须回传）。  
3. `auth.py` 或新依赖：解析 `X-User-Id`（可配置是否强制）。  
4. **入口同步改：** `main.py` 旧路径 + `harness/adapter/chat_http.py`（及 history/list 相关 API）；一律传入 `user_id`；history/list **必须鉴权或至少校验 user**。  
5. `run(...)` / `run_astream(...)`：若 `session_id` 为空 → 生成 UUID；写入与读取带上 `user_id`（Day1 可先把 user_id 传到 service，Day2 再落库）。  
6. 文档：README 注明必须传 `session_id` 或接收服务端下发的 id。

**过关手测：**

```text
1) 不传 session_id 聊一句 → 响应带新 session_id
2) 用该 id 再聊 → 有上下文
3) 换 X-User-Id，同 session_id（若已绑定用户）应 404/空（Day2 落库后强制）
4) HARNESS_RUNTIME 开/关两条路径行为一致（都不得落入 default）
```

Day1 若表尚未有 `user_id`：可先在进程内/服务层强制「空 session 就新建」，并删除代码路径上的 `"default"` 字面量；Day2 再做硬隔离。

---

### Mem-Day2 — 会话模型加固

1. `ChatSession` 增加 `user_id: str`（非空，默认迁移旧数据为 `anonymous`）。  
2. `updated_at`；可选 `status`。  
3. `get_or_create_session(session_id, user_id, db)`：查询条件含两者；插入唯一冲突则再读。  
4. `load_*` / `save_*` / `clear_*` / history API 全部带 `user_id`。  
5. `GET /sessions` 改为「仅当前用户的会话」，不要全表。  

**过关：** 用户 A 写入的 history，用户 B 用同一 `session_id` 读不到。

---

### Mem-Day3 — 历史读写拆分

1. `load_for_prompt(session_id, user_id, max_turns|budget)` → 给模型。  
2. `load_for_api(session_id, user_id, limit, offset)` → 给前端，默认按时间正序分页。  
3. 历史接口改用 `load_for_api`。  
4. `chat.py` 改用 `load_for_prompt`。

**过关：** DB 里 20 轮时，API 能翻到早期；Prompt 仍只有窗口内消息。

---

### Mem-Day4 — Token Budget + ContextBuilder

1. `config`：`context_token_budget`（如 3000）、`intent_history_turns`（如 2）。  
2. 实现简易估算：优先 `tiktoken`；没有则 `len(text)/2` 中文近似并注明。  
3. `app/services/context_builder.py`：`build_prompt_messages(...)` 从新到旧累加，超预算停止。  
4. `classify_intent` 只喂最近 `intent_history_turns`。  
5. `services/chat.py`（及 Crew `_format_history_text`）改走同一 builder。  
6. **禁止**在 `AgentRuntime` / Executor 协议层加记忆字段专判；Executor 继续吃装配好的 history。

**过关：** 构造一条超长 user 消息 + 多轮短消息，装配结果不超过预算；意图分类请求明显变短。

---

### Mem-Day5 — 元数据与挂接 Harness Run

1. 消息表加 `intent` / `engine` / `run_id` / `metadata`（JSONB）。  
2. `save_turn` 升级为 `save_turn(..., intent=, engine=, run_id=, metadata=)`；metadata 经脱敏。  
3. **`run_id` 来源：**  
   - Harness 路径：使用 Runtime 已生成的 `run_id`（`harness_runs` 主键），**禁止**再 `uuid4` 一套平行 ID。  
   - 旧路径 / 开关关闭：可本地生成，并尽量与后续落库策略一致。  
4. **不新建** `agent_runs` 表。工具轨迹、token 事件已在 `harness_run_events` 时，消息侧只存摘要或 `run_id` 引用。  
5. （可选）查库联表：`chat_messages.run_id` → `harness_runs`。

**过关：** 查库可见某条 assistant 消息的 intent/engine/run_id，且能在 `harness_runs`（若走 Harness）找到同行。

---

### Mem-Day6 — 滚动摘要

1. 表或字段 `session_summaries`。  
2. 当 prompt 窗口装不下且未摘要覆盖的旧消息超过阈值 → 调用 LLM 产出结构化 JSON。  
3. 装配时：`[摘要块] + [未摘要的最近原文]`。  
4. 摘要失败：打日志，本轮仍用纯截断，不阻断。

**过关：** 超过窗口的早期「我叫小明」在摘要后仍能被问到（允许表述压缩）。

---

### Mem-Day7 — RAG 追问改写

1. 若 `history` 非空：LLM/规则把当前问句改写成独立检索 query。  
2. `kb.search(rewritten)`；生成阶段仍可用原问句 + history。  
3. 改写失败则回退原 query。

**过关：** 先问退货规则，再问「那运费谁出」，检索 query 含退货/运费相关词。

---

### Mem-Day8 — Alarm 会话情景快照

1. `run_alarm_agent`（或 AlarmExecutor 成功路径）结束后写入 **session** 侧 `last_alarm_episode`。  
2. 路由到 alarm 且当前消息**不是**完整告警模板时：合并 episode 再跑（或走「追问」分支）。  
3. 明确哪些字段可追问复用（config_id、url、page）。  
4. **红线：** 不修改 `harness_checkpoints` 的 name/payload 约定；不把跨轮追问状态塞进同 Run checkpoint。  
5. 可选：episode 内记 `source_run_id`，便于审计。

**过关：** 完整告警跑完后，同会话发「看看第 2 页」能复用 config/url；进程内 resume 仍只依赖 H5 checkpoint（本步不测也不改）。

---

### Mem-Day9 — 缓存隔离

1. `SemanticCache.get/put` 增加 `scope`（`user_id` 或 `user_id:session_id`）。  
2. 命中必须 scope 一致。  
3. order/alarm/个性化结果默认不入共享逻辑（保持并加强现有跳过）。  
4. 与 H6 `CachePolicy` 薄壳并存时：以 SemanticCache 的 scope 为准，避免两套互斥逻辑。

**过关：** 用户 A 缓存的 knowledge 回答，用户 B 同类问题不命中 A 的条目。

---

### Mem-Day10 — 收尾

1. 单测：隔离、budget 裁剪、改写、cache scope；可选「消息 run_id 可关联 harness_runs」。  
2. README：记忆分层说明 + Header/`session_id` 约定 + 与 Harness Checkpoint 的边界。  
3. 本计划 Day 打勾；第二版入口指向完善计划中的 M4/M5（长期事实）与可选 LangGraph Checkpointer。
