# 新人完整学习与实施路线

默认你**会写代码**（尤其前端），但对「Python 后端 + RAG + 向量库 + Agent」还不熟。这份文档按阶段告诉你：**先学什么、学到什么程度、怎么自测、再去做哪几张任务卡**。

配套阅读：

| 你现在要… | 打开 |
|---|---|
| 看整盘节奏 | [计划总表.md](./计划总表.md) |
| 动手做事 | [任务清单.md](./任务清单.md) |

| 学概念（本文） | 每个阶段的「要掌握的知识」 |

**用法：** 进入某阶段 → 先把本文该阶段读完并做「过关自测」→ 再改任务清单状态为 `doing`。不要先抄参考项目再回头补概念，否则 FastAPI / Milvus / RAG 会混成一锅。

**总原则：** 参考项目只对照，不整仓复制。本项目会话必须进 PostgreSQL，向量必须进 Milvus。

## P1 存储底座（建议 3～4 天）

**阶段目标：** 会话能写入 PostgreSQL 并读回；一段文本变成向量后能被 Milvus 搜到。

**对应任务：** T-101～T-107

### 本阶段要掌握的知识

#### A. PostgreSQL 与后端数据层

| 知识 | 掌握到什么程度 |
|---|---|
| 表 / 主键 / 外键 / 索引 | 能看懂架构文档里的 4 张表，知道 `messages.session_id` 为什么要有索引 |
| UUID vs 业务 `session_key` | 对外用客户端字符串，对内用 UUID，避免主键被猜 |
| JSONB | `sources` 用 JSONB 存 `["a.md#1"]` |
| TIMESTAMPTZ | 一律带时区，按 `created_at` 取最近 N 条 |
| ORM vs 裸 SQL | 本项目用 SQLAlchemy 2；会定义 Model、写简单 `select` |
| 异步驱动 asyncpg | FastAPI 里不要用阻塞的 `psycopg2` 同步连库 |
| Alembic 迁移 | `revision` / `upgrade`；改表必须走迁移，不手工改线上 |
| Repository 模式 | 路由不直接写 SQL，会话记忆封装成 `get_messages` / `add` |

#### B. 向量与 Milvus

| 知识 | 掌握到什么程度 |
|---|---|
| Embedding | 一段话 → 一串浮点数；语义近则向量夹角小 |
| 维度 dim | 模型定死（如 768 / 1024）；Collection 的 dim 必须一致 |
| ANN 近似近邻 | 不扫全表，用索引找「最像」的 top-k |
| Collection / Field / Metric | 一个 Collection 类似一张表；常用 COSINE 或 IP |
| upsert vs insert | 同一 `chunk_id` 更新而不是重复插 |
| 向量库 vs 关系数据库 | Milvus 存向量和 id；**原文、文件名、会话**放 PostgreSQL |

务必建立这张图：

```
用户问题
  → Embedding 模型 → 查询向量
  → Milvus search → 得到 chunk_id 列表
  → PostgreSQL 按 id 取 content
  → 把 content 交给 LLM
```

### 建议学习顺序

1. 手写 SQL：建 `sessions`/`messages`，插入两轮对话，按时间查出最近 4 条。  
2. 把同样的事用 SQLAlchemy + Alembic 再做一遍。  
3. 读 Milvus 文档「Hello Milvus」：建 Collection、插 3 条假向量、search。  
4. 把 `chunk_id` 设计进 Field，search 后回表 PG（哪怕 PG 里先写死几行文本）。  
5. 写启动校验：embed 一条短文本，看 `len(vector) == collection.dim`。

### 过关自测

- [ ] 能画出「会话在 PG、向量在 Milvus、用 id 对齐」而不是「什么都塞进 Milvus」
- [ ] 重启 API 进程后，旧 `session_id` 仍能读到消息
- [ ] 故意用错 dim，服务应拒绝启动而不是检索永远为空
- [ ] 能说明：为什么本项目 **禁止** 启动时 drop Collection

### 先不要学

分块策略、BM25 公式、Reranker 模型结构。没有稳定的「存和取」，检索工程没有意义。

## P2 RAG 知识库（建议 4～5 天）

**阶段目标：** 上传文档 → 能按问题检索 → LLM **只根据资料**回答，并带来源。

**对应任务：** T-201～T-209

这是整个项目最核心的概念阶段，建议每天只啃一块。

### 本阶段要掌握的知识

#### 1. RAG 是什么（必须能给别人讲清楚）

检索增强生成：先从知识库找出相关段落，再让模型根据段落写答案。  
目的：减少胡编、答案可追溯。  
一句话：**检索负责找对，生成负责写好，Prompt 负责不许瞎编。**

#### 2. 解析与分块

| 知识 | 掌握到什么程度 |
|---|---|
| 解析 | PDF/DOCX 抽纯文本；MD/TXT 直接读 |
| 为什么要分块 | 模型上下文有限；检索粒度太粗会噪声大 |
| chunk_size / overlap | 本项目默认约 400 字、重叠 80；overlap 防止句子被切断 |
| Markdown 按标题切 | 一节一个语义块，比纯按字数切更适合帮助中心 |
| source 格式 | `文件名#块号`，ingest 必须用**原文件名** |

#### 3. 双路检索与融合

| 知识 | 掌握到什么程度 |
|---|---|
| 向量检索 | 同义句（「运费谁出」「谁承担运费」）靠语义命中 |
| BM25 + jieba | 专有名词、准确措辞靠词面命中；中文必须分词 |
| 为什么要混合 | 小知识库上纯向量常弱于 BM25（参考项目测过 67% vs 98%） |
| RRF | 不靠分数对齐，按「排名倒数」把两路结果合成一路 |
| 追加语料 | BM25 索引必须 extend，**不能**每次 ingest 覆盖整个 corpus |

#### 4. 重排（Reranker）

| 知识 | 掌握到什么程度 |
|---|---|
| 召回 vs 精排 | 先多拿候选（15+15），再用 CrossEncoder 打分留 top-k |
| 可降级 | 没装 torch / 下载失败就保留 RRF 顺序，服务不能挂 |

#### 5. RAG Prompt

| 知识 | 掌握到什么程度 |
|---|---|
| 约束 | 「只能依据资料；没有就说不知道」 |
| 注入 | `{context}` + `{question}` + `{history}` |
| 幻觉 | 资料没有时模型仍可能编，要用评测在 P6 抓 |

### 建议学习顺序

1. 只做解析+分块，打印块数和每块前 50 字。  
2. 只入库 PG + Milvus，用固定问题调 `search`，人工看命中对不对。  
3. 加上 BM25，对比三路命中（脚本 T-209）。  
4. 再接到 LLM 生成。最后才加 reranker。

### 过关自测

- [ ] 能讲清：没有检索、直接让模型答退货规则，和 RAG 差在哪里
- [ ] 二次上传另一篇文档后，第一篇仍能被 BM25 搜到
- [ ] `sources` 里是 `knowledge_base.md#2` 而不是 `tmp123.md#2`
- [ ] 问知识库没有的内容，回答会承认不知道（Prompt 生效）

### 先不要学

CrewAI、SSE 事件协议、RAGAS 四个指标的论文细节。P2 验收是「检索+生成对」，不是「多智能体」。

## P3 对话主链路（建议 4～5 天）

**阶段目标：** 用户能连续聊天；重启后同一 `session_id` 仍记得上下文；同步和流式是**同一套逻辑**。

**对应任务：** T-301～T-308

### 本阶段要掌握的知识

| 知识 | 掌握到什么程度 |
|---|---|
| 意图识别 | 用 LLM 把一句话分成 knowledge / order / chat；当路由器，不是知识库 |
| 分类必须带历史 | 「那运费谁出」离开上文会变成闲聊 |
| JSON 解析兜底 | 模型偶尔不按格式输出，失败则当 `chat`，服务不 500 |
| 会话记忆 | 存全部轮次（有上限裁剪），每次只把最近 N 轮放进 Prompt |
| `session_id` | 客户端生成并原样传回；默认值会导致所有人共用一个会话，要能讲出这个风险 |
| SSE | `text/event-stream`；一行 `data: {json}\n\n`；事件类型 stage / intent / token / done |
| 流式生成 | LangChain `astream` 逐 token；订单工具没有 token 流，整段当一次 token |
| Pipeline 模式 | 业务步骤只写一遍；JSON 等整段，SSE 订阅中间事件 |
| 工具（Tool） | 订单查询是函数调用，不是 RAG；动态结果禁止进语义缓存 |

前端对照：SSE 的 `token` 事件 ≈ 打字机输出；`stage` ≈ 前端 loading 步骤条。

### 建议学习顺序

1. 只做非流式：意图 → 三分支 → 写 PG。  
2. 用同一 `session_id` 连问两轮，确认第二轮 Prompt 里有第一轮。  
3. **重启 uvicorn**，再问第三轮，确认记忆来自数据库不是内存。  
4. 把同一 pipeline 接上 SSE，控制台或 curl 看事件顺序。  
5. 最后才加缓存（或放到 P5，但接口要留好钩子）。

### 过关自测

- [ ] 能画出 JSON 和 SSE 如何共用 `ChatPipeline`（一张图，不要两套 if/else）
- [ ] 杀掉进程再启动，追问仍正确
- [ ] 不装 CrewAI 时，整条客服链路已经可用（P4 只是增强）

### 先不要学

Agent 协作理论、十acity 重试分类。没有稳定对话，做 Agent 只会分叉出第二条链路。

## P4 多智能体（建议 2～3 天）

**阶段目标：** 理解「两个角色顺序协作」；会降级；**主路径仍然是 P3**。

**对应任务：** T-401～T-405

### 本阶段要掌握的知识

| 知识 | 掌握到什么程度 |
|---|---|
| Agent 是什么 | 带角色设定 + 可选工具的 LLM 调用，不是新的编程语言 |
| CrewAI 结构 | Agent（角色/目标/工具）+ Task（要干什么）+ Crew（怎么排程） |
| sequential | 意图官先跑，输出给执行员；不是互相辩论 |
| Tool | 普通 Python 函数包一层，供执行员决定调不调 |
| 降级 | 没装包 / 调用失败 → 自动走 P3，用户无感 |
| 线程池 | Crew 同步 `kickoff` 会阻塞，FastAPI 里要用 `asyncio.to_thread` |
| 和 LangGraph/CoAgents 的区别 | 本项目不用后两者；不要混概念 |

必须能讲清这条链：

```
用户
 → Agent1 意图识别官（无工具，只出 JSON）
 → Agent2 客服执行员（search_knowledge / query_order / after_sale_rule）
 → 最终中文答复写入 PostgreSQL
```

### 建议学习顺序

1. 读参考项目 `app/agents/crew.py` + `tools.py`，对照上面这条链。  
2. 先实现三个普通函数，不接 Crew。  
3. 再包 `@tool`，跑一次 sequential Crew。  
4. 最后接开关和 try/except 降级。

### 过关自测

- [ ] 能回答：这是不是多 Agent？——「是，但是两段顺序链，不是自主谈判」
- [ ] 卸载 crewai 后服务仍能问答
- [ ] Crew 路径也会写 PG，且尽量有 sources

### 先不要学

复杂 Multi-agent 论文、AutoGPT、浏览器操作 Agent。超出本项目范围。

## P5 稳定性、可观测、鉴权（建议 3～4 天）

**阶段目标：** 服务在限流/超时下可预期；能看见每一步花了多久；不能谁都能灌知识库。

**对应任务：** T-501～T-507

### 本阶段要掌握的知识

| 知识 | 掌握到什么程度 |
|---|---|
| 可重试 vs 不可重试 | 429/5xx/超时可重试；400/业务校验不可重试 |
| 指数退避 | 等 0.5s、1s… 上限封顶，避免打爆上游 |
| 滑动窗口限流 | 按 IP 统计 60 秒内次数；监控接口要豁免 |
| 语义缓存 | 向量相似 **并且** 词面也像才命中；阈值必须读配置 |
| 为什么订单不缓存 | 物流状态会变 |
| 为什么多轮不缓存 | 同一句在不同上下文答案不同 |
| 链路追踪 | 每阶段毫秒数；P95 比平均值更能说明「慢在尾部」 |
| API Key | 服务间鉴权，不是用户登录；保护 chat 和 ingest |

控制台：HTML/JS 你已有基础，重点是消费 SSE 的 `stage` 画步骤，轮询 `/stats`、`/traces`。不要上 React 脚手架（第一期不需要）。

### 过关自测

- [ ] 把缓存阈值写进 `.env` 后确实生效（参考项目这里是坑）
- [ ] 无 API Key 时 ingest 返回 401
- [ ] dashboard 能看到「检索里向量/BM25/融合/重排」各自耗时

### 先不要学

OpenTelemetry 全套、Prometheus、Redis 分布式限流。第一期进程内足够；多副本时再升级（计划总表「明确不做」）。

## P6 评测与交付（建议 3～4 天）

**阶段目标：** 能证明 RAG 效果、能自动检查、别人能按 README 跑起来。

**对应任务：** T-601～T-606

### 本阶段要掌握的知识

| 知识 | 掌握到什么程度 |
|---|---|
| 评测集 | 每条有问题、标准答案、关键词；要包含「库里没有」的题 |
| Faithfulness | 答案是否忠于检索到的上下文（防胡编） |
| AnswerRelevancy | 是否在回答这个问题 |
| ContextPrecision / Recall | 找来的段落准不准、全不全 |
| LLM-as-Judge | 另一次 LLM 打 1～5 分；省人力但有偏差 |
| 关键词命中基线 | 不依赖 RAGAS，检索对不对先有个数 |
| CI | push 后自动 install + 语法 + 单测；评测没 Key 就跳过 |
| 镜像分层 | 核心依赖进镜像；torch/rerank 默认关，保持镜像小 |
| 交付文档 | 别人只看 README 能配模型、起 compose、打通一轮对话 |

### 过关自测

- [ ] 能解释四个 RAGAS 指标各自在抓哪类问题
- [ ] CI 在没配云端 Key 时，build 和 test 仍然绿
- [ ] 一台干净机器按 README 能对话（你自己走一遍）

## 术语表（遇到单词就翻这里）

| 术语 | 人话 |
|---|---|
| LLM | 大语言模型，输入文本输出文本 |
| Embedding | 把文本变成一串数字，方便比「像不像」 |
| 向量库 / Milvus | 专门存这些数字并做相似搜索的数据库 |
| ANN | 近似最近邻，快速找最像的几条 |
| Collection | Milvus 里类似「表」 |
| RAG | 先从资料里找段落，再让模型根据段落回答 |
| chunk | 切出来的一小段资料 |
| BM25 | 按关键词匹配的经典检索 |
| RRF | 把两路排名合成一路的简单算法 |
| Reranker | 对候选段落再打一遍相关性分 |
| Hallucination / 幻觉 | 模型编造资料里没有的内容 |
| SSE | 服务器持续推事件，用于打字机式输出 |
| Agent | 带角色和工具的 LLM 调用单元 |
| Crew | CrewAI 里多个 Agent + 多个 Task 的一次编排 |
| 降级 | 高级能力失败时走备用实现，服务不停 |
| P95 | 95% 的请求比这个时间更快，看尾部延迟 |
| RAGAS | 一套给 RAG 打分的指标工具 |
