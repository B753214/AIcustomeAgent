## 二、这个项目到底是什么（先建立图像）

想象你要做一个**二手交易平台的智能客服接口**。用户在小程序/网页里问：

> 「退货运费谁承担？」

服务不能瞎编，要去**帮助中心文档**里找相关段落，再组织成客服口吻回答。如果用户问「订单 202608090001 到哪了」，就去调订单查询（第一期用假数据）。如果用户说「你好」，就闲聊。

用前端类比：

| 本项目 | 你可以把它想成 |
|---|---|
| FastAPI | NestJS / Express 后端 |
| `POST /api/v1/chat` | 一个普通 JSON 接口 |
| `POST /api/v1/chat/stream` | 用 SSE 做打字机效果（类似 EventSource） |
| PostgreSQL | 存聊天记录的业务库（类似你们的 MySQL） |
| Milvus | 专门存「文本的数字指纹」并搜相似句的库，不是替代 PostgreSQL |
| LangChain | 调大模型、拼 Prompt、接向量检索的工具库 |
| CrewAI | 可选：两个「角色」顺序干活（先分类再执行） |
| 控制台 dashboard.html | 一张本地 HTML，方便你试对话，不是给 C 端用户的 |

**一次提问在系统里怎么走（先记住这 6 格）：**

```
① 用户发消息 + session_id（会话编号）
② 限流、鉴权（P5 才做，前期可关）
③ 查一下有没有「很像的旧问题」可直接复用答案（语义缓存，P5）
④ 判断意图：知识问答 / 查订单 / 闲聊
⑤ 知识问答：去 Milvus+关键词 找出资料 → 让模型根据资料写答案
⑥ 把本轮用户问、客服答 写入 PostgreSQL，下次追问能带上原文
```

**两件必须记住的存储分工：**

- 聊天记录、文档原文、切出来的段落 → **PostgreSQL**（人能读的数据）  
- 每段资料对应的向量（一长串小数）→ **Milvus**（只负责「找相似」）  
- 两边用同一个 `chunk_id` 对齐：Milvus 找到 id，再回 PostgreSQL 取正文。

参考项目把聊天和向量都放在「进程内存」里，一重启就没了。我们要做成重启还在。

**成功长什么样：** `docker version` 有 Client 和 Server 两段；`docker ps` 能出一张表（可以没有容器，但不能报错连不上引擎）。

## 六、P1 存数据（步骤 P1-1 ～ P1-7）

目标：聊天能进 PostgreSQL；一段话能变成向量进 Milvus 并能搜回来。  
仍然**没有**完整客服问答。

### 步骤 P1-1　讲清四张表（先懂再建模）

我会按 [架构与数据模型.md](./架构与数据模型.md) 带你建表。人话版：

| 表 | 存什么 | 类比 |
|---|---|---|
| sessions | 一次会话的身份证 | 一个聊天窗口 |
| messages | 每一句用户/客服 | 窗口里的气泡 |
| documents | 上传过的文件 | 一篇帮助文档 |
| chunks | 切出来的小段文字 | 文档里的某一节 |

**你要明白：** 对外 API 仍用字符串 `session_id`；库里用 UUID 做主键。两套 id 不要混。

---

### 步骤 P1-2　Alembic 迁移

**目的：** 表结构的变更有版本，能升级/回滚。类似 Prisma migrate。

**你会执行：** `alembic upgrade head`，然后用客户端看到 4 张空表。

---

### 步骤 P1-3　Session 仓储：写入两轮对话再读出来

**目的：** 替换「内存字典」。

**验证脚本（到时提供）：** 写入 user/assistant 各两条，按 `session_key` 读最近 N 条，顺序正确。

**重启 API 后再读一次，数据还在 → 这一步才算过。**

---

### 步骤 P1-4　Chunk 仓储

**目的：** 分块正文以 PostgreSQL 为准，BM25 以后从这里加载。

---

### 步骤 P1-5　连上 Milvus，创建 Collection

**你要明白：**

- Collection ≈ 一张表  
- 必须有一列 `vector`，长度 `dim` 等于 Embedding 模型输出长度  
- 再存 `chunk_id`，才能回表查正文  

**我会带你做：** 启动时「没有就创建」，**绝不默认删除整个 Collection**。

---

### 步骤 P1-6　写入一条向量并 search

流程：

```
文本「退货运费由卖家承担」
  → Embedding 得到例如 1024 个数
  → upsert 进 Milvus（带 chunk_id）
  → 再用「运费谁出」embed 一次去 search
  → 应命中刚才那条
```

**你要明白：** 搜的是「意思相近」，不是精确字符串相等。

---

### 步骤 P1-7　启动时校验 dim

若你换了向量模型，旧 Collection 维度对不上，检索会 silently 全空。  
我们会在启动时 embed 一个字，检查 `len(向量) == collection.dim`，不对就直接报错退出。

**P1 验收：**  
- PG 能读写会话  
- Milvus 能写入并搜到  
- dim 错误能失败得明白

## 七、P2 知识库 RAG（步骤 P2-1 ～ P2-8）

这是最难、也最值得慢慢走的阶段。目标：上传文档，提问能根据文档回答。

### 先把 RAG 讲成三步（必须能复述）

1. **切：** 把长文档切成小段（chunk）。  
2. **找：** 用户问题变成向量，去 Milvus 找最像的几段；同时用关键词（BM25）再找几段；两路合并。  
3. **写：** 把找到的段落塞进 Prompt，告诉模型「只能根据这些写，没有就说不知道」。

没有第 2 步，模型就是在背训练数据，客服场景会乱说话。

---

### 步骤 P2-1　解析文件

PDF / Word / Markdown / 纯文本 → 得到一大段纯文本。  
缺某个解析库时，其它格式仍能用。

---

### 步骤 P2-2　分块

- Markdown：尽量按标题（`## 退货规则`）切。  
- 其它：大约 400 字一块，块与块重叠约 80 字，避免一句话被切断。  

**验证：** 打印每一块的前 80 个字和编号，你肉眼能看出切得是否合理。

---

### 步骤 P2-3　入库（关键：原文件名 + 两处写入）

顺序固定：

1. 在 PostgreSQL 写入 document + chunks（拿到 chunk 的 UUID）  
2. 对每块做 Embedding，写入 Milvus  
3. 把块文本 **追加** 进 BM25 索引（不能把旧文档覆盖掉）

上传接口必须用浏览器给的**原文件名** `退货.md`，不要用系统临时名 `tmp123.md`。  
否则来源会变成看不懂的 tmp，这是参考项目的坑。

---

### 步骤 P2-4　只检索、先不叫大模型

写一个内部函数：输入问题，输出若干段 `content` + `sources`。  
你用「退货运费谁承担」测，应能看到退货相关段落。  
这一步不过，不要接 LLM。

---

### 步骤 P2-5　BM25 中文词面检索

**你要明白：** 「七天无理由」这种专有说法，有时关键词比向量更准。  
jieba 负责把中文切开，BM25 给每段打分。

**验证：** 连续 ingest 两篇文档，第一篇的内容仍能被搜到（证明没有覆盖索引）。

---

### 步骤 P2-6　RRF 融合 + 可选重排

两路结果怎么合成一路：看排名，不看两套分数（分数不可比）。  
重排模型很大，装不上就跳过，顺序仍用融合结果。

---

### 步骤 P2-7　RAG 生成

Prompt 里写死：只能依据资料；资料没有就说不知道。  
返回答案 + `["knowledge_base.md#2"]` 这种来源。

---

### 步骤 P2-8　`POST /api/v1/ingest` + 示例知识库

放一篇和参考项目类似的 `data/knowledge_base.md`（发布商品、退货、运费等）。  
启动时：若库里还没有这篇，就自动导入；**已有则跳过**，且不清空 Milvus。

**P2 验收：** ingest 之后用临时 chat 或脚本提问，答案正确且 sources 是原文件名。

---

### 步骤 P3-1　画出统一 Pipeline（先设计后写）

禁止再写成：JSON 一套逻辑、SSE 又复制一套。  
正确结构：

```
ChatPipeline.run(message, session_id, on_event=None)
    读历史（PG）
    意图分类
    执行（RAG / 订单 / 闲聊）
    写回 PG
    若 on_event 存在，就把 stage/token 推出去（SSE）
    若没有，就等全部结束返回 JSON
```

---

### 步骤 P3-2　意图分类（带历史）

模型只许输出 JSON：`knowledge` / `order` / `chat`。  
解析失败就当 `chat`，不要 500。  
必须把最近几轮对话一起送给分类器，否则「那运费谁出」会被当成闲聊。

---

### 步骤 P3-3　三条执行分支

- knowledge → 走 P2 的 RAG  
- order → `query_order`（正则抽单号，第一期返回假物流）  
- chat → 客服闲聊 Prompt  

订单结果不进语义缓存（物流会变；缓存是 P5 的事，这里先留注释）。

---

### 步骤 P3-4　记忆读写接 PostgreSQL

每次生成用最近 6 轮（可配置），库里最多保留 20 轮，更旧的删掉。  
接口请求体：

```json
{ "message": "怎么退货？", "session_id": "user-001" }
```

不传 `session_id` 会落到默认值，所有人共用一个聊天记录——你要知道这是坑，演示时请自己传不同 id。

---

### 步骤 P3-5　`POST /api/v1/chat`

返回类似：

```json
{
  "reply": "……",
  "intent": "knowledge",
  "sources": ["knowledge_base.md#3"],
  "engine": "langchain",
  "used_crew": false,
  "cache_hit": false
}
```

---

### 步骤 P3-6　`POST /api/v1/chat/stream`（SSE）

事件顺序（和参考项目对齐，方便你对照控制台）：

1. `stage`：缓存 / 意图 / 检索 / 生成  
2. `intent`  
3. 多个 `token`（打字机）  
4. `done`

检索的 stage 里带上向量/BM25/融合/重排各自花了多少毫秒。

---

### 步骤 P3-7　验收剧本（必须亲手跑）

1. `session_id=demo-1` 问：怎么申请退货？  
2. 同一 id 再问：那运费谁出？ → 应仍是知识问答且答对。  
3. **重启 uvicorn**，同一 id 再问：我刚才问的是什么？ → 应能提到退货（证明记忆在 PG）。  
4. 换 `session_id=demo-2`，不应看到 demo-1 的内容。

通过后才允许做 P4。
