## 来源：计划总表（原 计划总表.md）

按一个人全职、可并行部分任务估算。周期可按实际节奏压缩或拉长，**阶段顺序不要打乱**：先基础设施，再 RAG，再编排，最后评测交付。

新人请同时打开 [学习路线.md](./学习路线.md)：每个阶段都是 **先掌握知识并过关 → 再做任务清单**。下表「本阶段要掌握」只是摘要，细则、过关自测、先不要学什么都在学习路线里。

## 总览

| 阶段 | 名称 | 建议周期 | 本阶段要掌握 | 核心产出 | 完成定义 |
|---|---|---|---|---|---|
| 开工前 | 公共底子 | 1～3 天 | Python/venv、HTTP、Docker 基础、LLM 常识 | 本机环境 | 能起容器、能调通一个模型或 Ollama |
| P0 | 工程脚手架 | 2～3 天 | FastAPI、lifespan、env 配置、Compose 服务名 | 空服务 + health | `/health` 能连上 Milvus 与 PostgreSQL |
| P1 | 存储底座 | 3～4 天 | PG 表/外键/JSONB、SQLAlchemy、Alembic；Embedding、dim、Milvus Collection | 会话与向量可持久化 | 能写入一条会话、能写入一条向量并检索 |
| P2 | RAG 知识库 | 4～5 天 | RAG、分块、向量 vs BM25、RRF、重排、防幻觉 Prompt | 入库 + 混合检索 + 生成 | 上传 MD 后提问能命中并带来源 |
| P3 | 对话主链路 | 4～5 天 | 意图路由、多轮记忆、SSE、统一 Pipeline、Tool | 同步 + 流式对话 | 同一 `session_id` 重启后仍能追问 |
| P4 | 多智能体 | 2～3 天 | Agent/Task/Crew、sequential、降级、to_thread | 双 Agent + 降级 | 未装 crewai 时服务仍可用 |
| P5 | 稳定性与控制台 | 3～4 天 | 重试分类、限流、语义缓存、P95、API Key | 可观测 + 鉴权 | 控制台能看阶段耗时；ingest 需 API Key |
| P6 | 评测与交付 | 3～4 天 | RAGAS 四指标、Judge、CI、镜像分层 | 评测 + 一键部署 | CI 过语法+单测；compose 能拉起全栈 |

合计约 **3.5～4.5 周**。P2 与 P1 后半可部分重叠；P4 可在 P3 验收后再做，避免两套对话逻辑先分叉。

### P1 存储底座

**先学：** [学习路线 · P1](./学习路线.md#p1-存储底座建议-3～4-天)（PostgreSQL + Embedding + Milvus）

| 项 | 说明 |
|---|---|
| 要掌握 | 四张表的职责；异步 ORM 与迁移；向量、维度、ANN、Collection；「原文在 PG、向量在 Milvus、id 对齐」 |
| 要做 | PostgreSQL：`sessions` / `messages` / `documents` / `chunks`；Alembic；异步仓储接口。Milvus：建 Collection、upsert、similarity search。启动时 **不** 清空 Collection（与参考项目 `RESET_ON_START=true` 相反，本项目要持久化） |

## P1 存储底座（建议 3～4 天）

**阶段目标：** 会话能写入 PostgreSQL 并读回；一段文本变成向量后能被 Milvus 搜到。

**对应任务：** T-101～T-107

### 本阶段要掌握的知识

#### A. PostgreSQL 与后端数据层

| 知识 | 掌握到什么程度 |
|---|---|
| 表 / 主键 / 外键 / 索引 | 能看懂架构文档里的 4 张表，知道 `messages.session_id` 为什么要有索引 |
| UUID vs 业务 `session_key` | 对外用客户端字符串，对内用 UUID，避免主键被猜 |
| JSONB | `sources` 用 JSONB 存 `["a.md#1"]` |
| TIMESTAMPTZ | 一律带时区，按 `created_at` 取最近 N 条 |
| ORM vs 裸 SQL | 本项目用 SQLAlchemy 2；会定义 Model、写简单 `select` |
| 异步驱动 asyncpg | FastAPI 里不要用阻塞的 `psycopg2` 同步连库 |
| Alembic 迁移 | `revision` / `upgrade`；改表必须走迁移，不手工改线上 |
| Repository 模式 | 路由不直接写 SQL，会话记忆封装成 `get_messages` / `add` |

#### B. 向量与 Milvus

| 知识 | 掌握到什么程度 |
|---|---|
| Embedding | 一段话 → 一串浮点数；语义近则向量夹角小 |
| 维度 dim | 模型定死（如 768 / 1024）；Collection 的 dim 必须一致 |
| ANN 近似近邻 | 不扫全表，用索引找「最像」的 top-k |
| Collection / Field / Metric | 一个 Collection 类似一张表；常用 COSINE 或 IP |
| upsert vs insert | 同一 `chunk_id` 更新而不是重复插 |
| 向量库 vs 关系数据库 | Milvus 存向量和 id；**原文、文件名、会话**放 PostgreSQL |

务必建立这张图：

```
用户问题
  → Embedding 模型 → 查询向量
  → Milvus search → 得到 chunk_id 列表
  → PostgreSQL 按 id 取 content
  → 把 content 交给 LLM
```

### 建议学习顺序

1. 手写 SQL：建 `sessions`/`messages`，插入两轮对话，按时间查出最近 4 条。  
2. 把同样的事用 SQLAlchemy + Alembic 再做一遍。  
3. 读 Milvus 文档「Hello Milvus」：建 Collection、插 3 条假向量、search。  
4. 把 `chunk_id` 设计进 Field，search 后回表 PG（哪怕 PG 里先写死几行文本）。  
5. 写启动校验：embed 一条短文本，看 `len(vector) == collection.dim`。

### 过关自测

- [ ] 能画出「会话在 PG、向量在 Milvus、用 id 对齐」而不是「什么都塞进 Milvus」
- [ ] 重启 API 进程后，旧 `session_id` 仍能读到消息
- [ ] 故意用错 dim，服务应拒绝启动而不是检索永远为空
- [ ] 能说明：为什么本项目 **禁止** 启动时 drop Collection

### 先不要学

分块策略、BM25 公式、Reranker 模型结构。没有稳定的「存和取」，检索工程没有意义。

## P2 RAG 知识库（建议 4～5 天）

**阶段目标：** 上传文档 → 能按问题检索 → LLM **只根据资料**回答，并带来源。

**对应任务：** T-201～T-209

这是整个项目最核心的概念阶段，建议每天只啃一块。

### 本阶段要掌握的知识

#### 1. RAG 是什么（必须能给别人讲清楚）

检索增强生成：先从知识库找出相关段落，再让模型根据段落写答案。  
目的：减少胡编、答案可追溯。  
一句话：**检索负责找对，生成负责写好，Prompt 负责不许瞎编。**

#### 2. 解析与分块

| 知识 | 掌握到什么程度 |
|---|---|
| 解析 | PDF/DOCX 抽纯文本；MD/TXT 直接读 |
| 为什么要分块 | 模型上下文有限；检索粒度太粗会噪声大 |
| chunk_size / overlap | 本项目默认约 400 字、重叠 80；overlap 防止句子被切断 |
| Markdown 按标题切 | 一节一个语义块，比纯按字数切更适合帮助中心 |
| source 格式 | `文件名#块号`，ingest 必须用**原文件名** |

#### 3. 双路检索与融合

| 知识 | 掌握到什么程度 |
|---|---|
| 向量检索 | 同义句（「运费谁出」「谁承担运费」）靠语义命中 |
| BM25 + jieba | 专有名词、准确措辞靠词面命中；中文必须分词 |
| 为什么要混合 | 小知识库上纯向量常弱于 BM25（参考项目测过 67% vs 98%） |
| RRF | 不靠分数对齐，按「排名倒数」把两路结果合成一路 |
| 追加语料 | BM25 索引必须 extend，**不能**每次 ingest 覆盖整个 corpus |

#### 4. 重排（Reranker）

| 知识 | 掌握到什么程度 |
|---|---|
| 召回 vs 精排 | 先多拿候选（15+15），再用 CrossEncoder 打分留 top-k |
| 可降级 | 没装 torch / 下载失败就保留 RRF 顺序，服务不能挂 |

#### 5. RAG Prompt

| 知识 | 掌握到什么程度 |
|---|---|
| 约束 | 「只能依据资料；没有就说不知道」 |
| 注入 | `{context}` + `{question}` + `{history}` |
| 幻觉 | 资料没有时模型仍可能编，要用评测在 P6 抓 |

### 建议学习顺序

1. 只做解析+分块，打印块数和每块前 50 字。  
2. 只入库 PG + Milvus，用固定问题调 `search`，人工看命中对不对。  
3. 加上 BM25，对比三路命中（脚本 T-209）。  
4. 再接到 LLM 生成。最后才加 reranker。

### 过关自测

- [ ] 能讲清：没有检索、直接让模型答退货规则，和 RAG 差在哪里
- [ ] 二次上传另一篇文档后，第一篇仍能被 BM25 搜到
- [ ] `sources` 里是 `knowledge_base.md#2` 而不是 `tmp123.md#2`
- [ ] 问知识库没有的内容，回答会承认不知道（Prompt 生效）

### 先不要学

CrewAI、SSE 事件协议、RAGAS 四个指标的论文细节。P2 验收是「检索+生成对」，不是「多智能体」。

## P3 对话主链路（建议 4～5 天）

**阶段目标：** 用户能连续聊天；重启后同一 `session_id` 仍记得上下文；同步和流式是**同一套逻辑**。

**对应任务：** T-301～T-308

### 本阶段要掌握的知识

| 知识 | 掌握到什么程度 |
|---|---|
| 意图识别 | 用 LLM 把一句话分成 knowledge / order / chat；当路由器，不是知识库 |
| 分类必须带历史 | 「那运费谁出」离开上文会变成闲聊 |
| JSON 解析兜底 | 模型偶尔不按格式输出，失败则当 `chat`，服务不 500 |
| 会话记忆 | 存全部轮次（有上限裁剪），每次只把最近 N 轮放进 Prompt |
| `session_id` | 客户端生成并原样传回；默认值会导致所有人共用一个会话，要能讲出这个风险 |
| SSE | `text/event-stream`；一行 `data: {json}\n\n`；事件类型 stage / intent / token / done |
| 流式生成 | LangChain `astream` 逐 token；订单工具没有 token 流，整段当一次 token |
| Pipeline 模式 | 业务步骤只写一遍；JSON 等整段，SSE 订阅中间事件 |
| 工具（Tool） | 订单查询是函数调用，不是 RAG；动态结果禁止进语义缓存 |

前端对照：SSE 的 `token` 事件 ≈ 打字机输出；`stage` ≈ 前端 loading 步骤条。

### 建议学习顺序

1. 只做非流式：意图 → 三分支 → 写 PG。  
2. 用同一 `session_id` 连问两轮，确认第二轮 Prompt 里有第一轮。  
3. **重启 uvicorn**，再问第三轮，确认记忆来自数据库不是内存。  
4. 把同一 pipeline 接上 SSE，控制台或 curl 看事件顺序。  
5. 最后才加缓存（或放到 P5，但接口要留好钩子）。

### 过关自测

- [ ] 能画出 JSON 和 SSE 如何共用 `ChatPipeline`（一张图，不要两套 if/else）
- [ ] 杀掉进程再启动，追问仍正确
- [ ] 不装 CrewAI 时，整条客服链路已经可用（P4 只是增强）

### 先不要学

Agent 协作理论、十acity 重试分类。没有稳定对话，做 Agent 只会分叉出第二条链路。

## 二、这个项目到底是什么（先建立图像）

想象你要做一个**二手交易平台的智能客服接口**。用户在小程序/网页里问：

> 「退货运费谁承担？」

服务不能瞎编，要去**帮助中心文档**里找相关段落，再组织成客服口吻回答。如果用户问「订单 202608090001 到哪了」，就去调订单查询（第一期用假数据）。如果用户说「你好」，就闲聊。

用前端类比：

| 本项目 | 你可以把它想成 |
|---|---|
| FastAPI | NestJS / Express 后端 |
| `POST /api/v1/chat` | 一个普通 JSON 接口 |
| `POST /api/v1/chat/stream` | 用 SSE 做打字机效果（类似 EventSource） |
| PostgreSQL | 存聊天记录的业务库（类似你们的 MySQL） |
| Milvus | 专门存「文本的数字指纹」并搜相似句的库，不是替代 PostgreSQL |
| LangChain | 调大模型、拼 Prompt、接向量检索的工具库 |
| CrewAI | 可选：两个「角色」顺序干活（先分类再执行） |
| 控制台 dashboard.html | 一张本地 HTML，方便你试对话，不是给 C 端用户的 |

**一次提问在系统里怎么走（先记住这 6 格）：**

```
① 用户发消息 + session_id（会话编号）
② 限流、鉴权（P5 才做，前期可关）
③ 查一下有没有「很像的旧问题」可直接复用答案（语义缓存，P5）
④ 判断意图：知识问答 / 查订单 / 闲聊
⑤ 知识问答：去 Milvus+关键词 找出资料 → 让模型根据资料写答案
⑥ 把本轮用户问、客服答 写入 PostgreSQL，下次追问能带上原文
```

**两件必须记住的存储分工：**

- 聊天记录、文档原文、切出来的段落 → **PostgreSQL**（人能读的数据）  
- 每段资料对应的向量（一长串小数）→ **Milvus**（只负责「找相似」）  
- 两边用同一个 `chunk_id` 对齐：Milvus 找到 id，再回 PostgreSQL 取正文。

参考项目把聊天和向量都放在「进程内存」里，一重启就没了。我们要做成重启还在。

### 步骤 P1-1　讲清四张表（先懂再建模）

我会按 [架构与数据模型.md](./架构与数据模型.md) 带你建表。人话版：

| 表 | 存什么 | 类比 |
|---|---|---|

**你要明白：** 对外 API 仍用字符串 `session_id`；库里用 UUID 做主键。两套 id 不要混。

```
文本「退货运费由卖家承担」
  → Embedding 得到例如 1024 个数
  → upsert 进 Milvus（带 chunk_id）
  → 再用「运费谁出」embed 一次去 search
  → 应命中刚才那条
```

**你要明白：** 搜的是「意思相近」，不是精确字符串相等。

---

### 步骤 P1-7　启动时校验 dim

若你换了向量模型，旧 Collection 维度对不上，检索会 silently 全空。  
我们会在启动时 embed 一个字，检查 `len(向量) == collection.dim`，不对就直接报错退出。

**P1 验收：**  
- PG 能读写会话  
- Milvus 能写入并搜到  
- dim 错误能失败得明白  

---

## 七、P2 知识库 RAG（步骤 P2-1 ～ P2-8）

这是最难、也最值得慢慢走的阶段。目标：上传文档，提问能根据文档回答。

### 先把 RAG 讲成三步（必须能复述）

1. **切：** 把长文档切成小段（chunk）。  
2. **找：** 用户问题变成向量，去 Milvus 找最像的几段；同时用关键词（BM25）再找几段；两路合并。  
3. **写：** 把找到的段落塞进 Prompt，告诉模型「只能根据这些写，没有就说不知道」。

没有第 2 步，模型就是在背训练数据，客服场景会乱说话。

---

### 步骤 P2-1　解析文件

PDF / Word / Markdown / 纯文本 → 得到一大段纯文本。  
缺某个解析库时，其它格式仍能用。

---

### 步骤 P2-2　分块

- Markdown：尽量按标题（`## 退货规则`）切。  
- 其它：大约 400 字一块，块与块重叠约 80 字，避免一句话被切断。  

**验证：** 打印每一块的前 80 个字和编号，你肉眼能看出切得是否合理。

---

### 步骤 P2-3　入库（关键：原文件名 + 两处写入）

顺序固定：

1. 在 PostgreSQL 写入 document + chunks（拿到 chunk 的 UUID）  
2. 对每块做 Embedding，写入 Milvus  
3. 把块文本 **追加** 进 BM25 索引（不能把旧文档覆盖掉）

上传接口必须用浏览器给的**原文件名** `退货.md`，不要用系统临时名 `tmp123.md`。  
否则来源会变成看不懂的 tmp，这是参考项目的坑。

---

### 步骤 P2-4　只检索、先不叫大模型

写一个内部函数：输入问题，输出若干段 `content` + `sources`。  
你用「退货运费谁承担」测，应能看到退货相关段落。  
这一步不过，不要接 LLM。

---

### 步骤 P2-5　BM25 中文词面检索

**你要明白：** 「七天无理由」这种专有说法，有时关键词比向量更准。  
jieba 负责把中文切开，BM25 给每段打分。

**验证：** 连续 ingest 两篇文档，第一篇的内容仍能被搜到（证明没有覆盖索引）。

---

### 步骤 P2-6　RRF 融合 + 可选重排

两路结果怎么合成一路：看排名，不看两套分数（分数不可比）。  
重排模型很大，装不上就跳过，顺序仍用融合结果。

---

### 步骤 P2-7　RAG 生成

Prompt 里写死：只能依据资料；资料没有就说不知道。  
返回答案 + `["knowledge_base.md#2"]` 这种来源。

---

### 步骤 P2-8　`POST /api/v1/ingest` + 示例知识库

放一篇和参考项目类似的 `data/knowledge_base.md`（发布商品、退货、运费等）。  
启动时：若库里还没有这篇，就自动导入；**已有则跳过**，且不清空 Milvus。

**P2 验收：** ingest 之后用临时 chat 或脚本提问，答案正确且 sources 是原文件名。

---

## 八、P3 真正对话（步骤 P3-1 ～ P3-7）

目标：对外两个接口都能聊；重启不丢记忆。  
**做完这一阶段，你已经有可用产品。**

### 步骤 P3-1　画出统一 Pipeline（先设计后写）

禁止再写成：JSON 一套逻辑、SSE 又复制一套。  
正确结构：

```
ChatPipeline.run(message, session_id, on_event=None)
    读历史（PG）
    意图分类
    执行（RAG / 订单 / 闲聊）
    写回 PG
    若 on_event 存在，就把 stage/token 推出去（SSE）
    若没有，就等全部结束返回 JSON
```

---

### 步骤 P3-2　意图分类（带历史）

模型只许输出 JSON：`knowledge` / `order` / `chat`。  
解析失败就当 `chat`，不要 500。  
必须把最近几轮对话一起送给分类器，否则「那运费谁出」会被当成闲聊。

---

### 步骤 P3-3　三条执行分支

- knowledge → 走 P2 的 RAG  
- order → `query_order`（正则抽单号，第一期返回假物流）  
- chat → 客服闲聊 Prompt  

订单结果不进语义缓存（物流会变；缓存是 P5 的事，这里先留注释）。

---

### 步骤 P3-4　记忆读写接 PostgreSQL

每次生成用最近 6 轮（可配置），库里最多保留 20 轮，更旧的删掉。  
接口请求体：

```json
{ "message": "怎么退货？", "session_id": "user-001" }
```

不传 `session_id` 会落到默认值，所有人共用一个聊天记录——你要知道这是坑，演示时请自己传不同 id。

---

### 步骤 P3-5　`POST /api/v1/chat`

返回类似：

```json
{
  "reply": "……",
  "intent": "knowledge",
  "sources": ["knowledge_base.md#3"],
  "engine": "langchain",
  "used_crew": false,
  "cache_hit": false
}
```

---

### 步骤 P3-6　`POST /api/v1/chat/stream`（SSE）

事件顺序（和参考项目对齐，方便你对照控制台）：

1. `stage`：缓存 / 意图 / 检索 / 生成  
2. `intent`  
3. 多个 `token`（打字机）  
4. `done`

检索的 stage 里带上向量/BM25/融合/重排各自花了多少毫秒。

---

### 步骤 P3-7　验收剧本（必须亲手跑）

1. `session_id=demo-1` 问：怎么申请退货？  
2. 同一 id 再问：那运费谁出？ → 应仍是知识问答且答对。  
3. **重启 uvicorn**，同一 id 再问：我刚才问的是什么？ → 应能提到退货（证明记忆在 PG）。  
4. 换 `session_id=demo-2`，不应看到 demo-1 的内容。

通过后才允许做 P4。

## 十、P5 稳定、看得见、能挡住乱传（步骤 P5-1 ～ P5-6）

### 步骤 P5-1　重试

只对「网络抖、429、5xx」重试；用户问题本身不合法不要重试。

### 步骤 P5-2　按 IP 限流

60 秒内超过 N 次返回 429。health/stats/traces 不要限，否则控制台把自己卡死。

有聊天历史时不用缓存；订单不用缓存。

你熟悉前端：一页 HTML，输入框 + SSE 渲染 + 展示 stage。不要上 React。

### 步骤 P5-6　API Key

保护 chat 和 ingest。开发期可用开关关掉。没有 Key 谁都能灌知识库。
